# 第一部分　10-1 信号与优雅停止

## Q1　为什么要用信号做优雅停止？直接 Ctrl+C 或者 kill 不行吗？

### 1.1 先纠一个词：信号量 ≠ 信号

| | 是什么 | 在本工程里 |
| --- | --- | --- |
| 信号 signal | 内核发给进程的异步通知，靠编号识别：SIGINT=2、SIGTERM=15、SIGKILL=9 | 10-1 的主角，signalfd 读的就是它 |
| 信号量 semaphore | 带计数值的同步原语（P/V 操作），用于互斥或资源计数 | **没有使用**。线程池用的是 mutex + deque + 条件变量 + `outstanding_` 计数 |

### 1.2 关键反转：Ctrl+C 和 kill 本身就是信号

不存在"用信号"还是"直接用 Ctrl+C / kill"这个二选一。

| 你的动作 | 内核实际送出的 | 进程默认反应 |
| --- | --- | --- |
| 终端按 Ctrl+C | SIGINT (2)，发给**前台进程组** | 立刻终止，退出码 130 |
| `kill <pid>` | SIGTERM (15)（默认） | 立刻终止，退出码 143 |
| `kill -9 <pid>` | SIGKILL (9) | 立刻终止，**任何代码都拦不住** |

**所以问题不是"信号送不到"，而是"送到之后程序做什么"。**

### 1.3 "默认立刻死"具体死在哪里

默认终止不等于 `return 0`：不跑 C++ 栈展开、不执行析构。

- 退出码是 130 / 143，不是 0
- worker 线程被一起带走，刚算出的结果蒸发
- `outstanding_` 里的已接受任务再也没人取回
- `Connection::output` 中没发完的字节被丢弃，客户端永远等不到响应

对照 10-1 的观察记录：客户端"收到 201、202 约 5.01 秒的 ok，204、205 约 10.02 秒的 ok"——**这四条 ok 正是"直接 Ctrl+C"会丢掉的东西**。

### 1.4 那装一个信号处理函数不就行了？—— 为什么不行

信号 handler 能在**任意两条指令之间**插进来执行：

| 在 handler 里做 | 后果 |
| --- | --- |
| 遍历 `connections` 表 | 信号可能正好打断在同一张表的 `erase` 中间，遍历一个改到一半的容器 |
| `std::cout << ...` | 可能打断在 cout 自己的缓冲和锁内部 → 死锁或输出损坏 |
| 抛异常 | 从信号上下文抛异常，行为未定义 |
| 分配内存 | 可能打断在 malloc 内部 → 堆损坏 |

所以 POSIX 规定 handler 里只能调用少数 **async-signal-safe** 函数（`write`、`_exit` 等）。

多线程还多一层不确定：信号是进程级语义，但内核只挑**一条没屏蔽它的线程**递送。worker 手上可能正拿着 pool 的 mutex。

### 1.5 10-1 的解法：把"异步打断"降级成"fd 可读"

```text
pthread_sigmask(SIG_BLOCK)   ← 所有线程都不触发默认动作，信号变 pending
      ↓
signalfd                     ← pending 的信号变成一个可读的 fd
      ↓
塞进已有的 epoll             ← 和 listener、eventfd 平级的第三种事件源
      ↓
begin_stop() 在事件循环里被普通地调用一次
```

**核心收益**：`begin_stop` 跑在正常控制流里，connections 稳定、锁没被别人拿着，可以放心用 `std::cout` 和已有数据结构。

这就是"用信号做优雅停止"的真正含义——**不在 handler 里干活，而是把信号翻译成一个能在安全点处理的普通事件**。

前身对比：老的 self-pipe trick 和"handler 里只写一个 `volatile sig_atomic_t` 标志位"是同一个思想。signalfd 的好处是不用自建管道、不用管管道写满、能带回 siginfo、能直接进 epoll，且与"全线程屏蔽"自洽。

### 1.6 SIGKILL 为什么永远不能优雅

内核直接销毁进程，不给执行任何一行代码的机会。进程管理器（systemd、`docker stop`）的套路是：先 SIGTERM 给宽限期，到点还没退再 SIGKILL。

**优雅停止永远是合作式的**——没有人能强迫一条卡在 OpenCV 调用里的线程返回。

### 1.7 一句话收尾

kill 只能替你**送一个通知**，它没法替你"读完成 outstanding、发完 output、join 掉 worker、`return 0`"。真正的对立面不是"信号 vs kill"，而是：

> kill 送来的这个信号，你的程序是走内核默认动作**硬死**，还是走你自己写的收尾流程**有序退**。

## Q2　想让服务端自动停止，可以怎么做？

### 2.1 核心区分：触发源 vs 执行者

10-1 已经造好了**执行者**：`begin_stop()` + 联合退出条件 + pool 析构时 join + `return 0`。

"自动停止"只需要**换掉触发源**，让某个东西自动把停止请求送进 signalfd。**不要为了"自动"另写一条退出路径**——一旦走到点直接 `break` 或 `_exit(0)`，10-1 的排空逻辑就全废了。

### 2.2 三类触发源

| 触发源 | 具体做法 | 收尾由谁执行 |
| --- | --- | --- |
| **进程外监管者** | `timeout -s TERM -k 10s 30s ./server` | 进程自己（走 signalfd） |
| | systemd 的 `RuntimeMaxSec=` / `TimeoutStopSec=` | 同上 |
| | `docker stop -t 30` | 同上 |
| **自己的脚本** | 启动服务端 → 跑客户端 → `kill -TERM $PID` → `wait $PID` | 同上 |
| **服务端自己** | 事件循环里记 deadline，到点 `::raise(SIGTERM)` | 同上 |
| | 空闲超时退出（无连接无任务持续 N 秒） | 同上 |
| | 处理满 N 个请求就退（批处理模式） | 同上 |
| | `check_health()` 发现 `fatal_` 时转成停止流程 | 同上 |

最后一行的现状：`vision_pool_server.cpp` 目前 catch 到异常直接 `return 1`，**失败路径反而跳过了收尾**。这是最该补的一个"自动停止"分支。

### 2.3 最省事的一条路（不改服务端代码）

```bash
cd /home/rikanshin/VisionFlow/VisionFlow_learn
timeout --preserve-status -s TERM -k 10s 30s ./build/vision_pool_server --demo-delay-ms 5000
```

30 秒后送 SIGTERM（触发优雅收尾），再等 10 秒还不退就 SIGKILL 兜底。一条命令演示完整的两级机制。

**必须知道的坑**（已在机器上验证）：

```text
timeout 1 sleep 5                    → shell 看到 124
timeout --preserve-status 1 sleep 5  → shell 看到 143
```

`timeout` 默认把退出码**改写成 124**，会让 10-1 的 `echo $?` 验证方法失效。加 `--preserve-status` 才原样透传命令自己的退出码——服务端优雅退出是 0，你就能看到 0。

### 2.4 让服务端"自己到点下班"

在事件循环里加运行时长上限，到点不要直接调 `begin_stop`，而是：

```cpp
::raise(SIGTERM);   // 或 ::kill(::getpid(), SIGTERM)
```

因为所有线程都屏蔽了 SIGTERM，这个信号立刻变成 pending，signalfd 变可读，**下轮 epoll 用现有代码读出它，走现有 begin_stop**。零新增收尾代码，日志和幂等逻辑只有一份。

- 优点：停止请求永远只有一条入口
- 代价：依赖"信号保持屏蔽"这个前提；哪天 `pthread_sigmask` 被删了，`raise(SIGTERM)` 就变成默认动作直接硬杀
- 备选：直接调用 `begin_stop(SIGTERM, ...)`，更直白，但多一条触发入口要自己保证不重复

### 2.5 两条铁律

1. **自动化比手动更离不开宽限期兜底。** 人按 Ctrl+C 会盯日志决定要不要再按；脚本不会。而 10-1 的收尾是合作式的：某个 OpenCV 调用永不返回，`outstanding_` 就永远不为 0。所以 `-k`、`TimeoutStopSec`、`docker stop -t` 这类第二级 SIGKILL **不是可选项，是配套件**。
2. **脚本里 `kill -TERM $PID` 之后必须 `wait`。** kill 只是把信投进邮箱，命令返回不代表服务端已收尾完。不等就往下走，会在服务端还在发响应时删临时目录、或让新实例去抢 19090。

## Q3　集中理解检查第 1 题：pthread_sigmask 三问

### 3.1 会把主线程睡住吗？—— 不会

`pthread_sigmask` 只做一件事：**改调用线程的信号屏蔽位掩码，改完立刻返回**。不 sleep、不等待、不让出 CPU。

术语陷阱：POSIX 里 "block a signal" 的 block 是**"拦截、搁置"**，不是"卡住"。

| 调用 | 线程真的会停吗 |
| --- | --- |
| `mutex.lock()` 阻塞 | 会，停在那里等别人放锁 |
| `cv.wait()` 阻塞 | 会，挂起等通知 |
| `pthread_sigmask(SIG_BLOCK, …)` "阻塞" | **不会**，纯拨开关 |

三种状态必须分清：

| 处置 | 信号的下场 | 怎么产生 |
| --- | --- | --- |
| 屏蔽 blocked | 不按通常方式递送，**保留成 pending** | `pthread_sigmask(SIG_BLOCK)` |
| 忽略 ignored | **直接丢弃**，不 pending，读不到 | `signal(SIGINT, SIG_IGN)` |
| 处理 handled | 调用你装的 handler | `sigaction()` |

**屏蔽 ≠ 忽略**：屏蔽是"先压着，回头我自己取"，忽略是"当没发生过"。

正因为是"压着"，在 signalfd 建好之前按的 Ctrl+C 也不会丢，会一直 pending 到事件循环第一轮 `take_stop_signal` 把它读走。

补充：标准信号（非实时信号）**相同**的多条会合并成一条 pending，按五次 Ctrl+C 不等于收到五条——对应讲义"不把第二次 Ctrl+C 定义为强制终止"的设计。

现实 footgun：屏蔽了却忘了建 signalfd，Ctrl+C 就"按了没反应"，用户只能 `kill -9`——**你把默认的救命出口给关了**。

### 3.2 为什么必须在创建工作线程之前调用？

根本原因：**信号是进程级的语义，但屏蔽集合是线程级的属性。**

内核递送一个进程级信号的规则是：**从所有"没屏蔽它"的线程里挑一条**执行默认动作。它不特别照顾主线程。

正确顺序的因果链：

```text
主线程先屏蔽 → 两条 worker 线程“出生”时继承这个屏蔽集合
            → 全进程没有任何线程会触发默认动作
            → 信号只能 pending → 只能被 signalfd 读走
```

反过来的后果：先建 pool，再回来只屏蔽主线程——那两条**已经存在**的 worker 不会自动跟着变。Ctrl+C 到来时内核可能把 SIGINT 递给 worker，**默认动作立刻触发，整个进程当场死**，`begin_stop` 一行都不会跑。

关键理解：这不是"给所有线程设置全局开关"，而是**"给还没出生的线程设默认值"**。晚一步就补不回来。类比 `umask` 那种继承式设置，不是广播式的。

### 3.3 为什么不能直接套 check_call？

`check_call` 编码的是 **syscall 约定**：失败返回 -1，错误码写进 `errno`。

```cpp
void check_call(int result, const char* message) {
    if (result < 0) {
        throw std::system_error(errno, std::generic_category(), message);
    }
}
```

但 **`pthread_*` 系列不遵守这个约定**：

| 函数族 | 成功 | 失败 | errno |
| --- | --- | --- | --- |
| syscall（`socket`/`read`/`sigemptyset`…） | 0 或 fd | **-1** | **写入**错误码 |
| `pthread_*`（`pthread_sigmask`…） | **0** | **直接返回错误编号**（正数，如 EINVAL=22） | **不写** |

套 check_call 会同时中两枪：

1. **失败被静默放行。** `pthread_sigmask` 失败返回正数 22，`result < 0` 不成立，check_call 判定"成功"，程序若无其事继续跑。一个本该当场炸掉的错误，变成几十分钟后一个无法解释的现象。
2. **错误信息张冠李戴。** 就算改成 `!= 0`，也不能读 errno——pthread 函数不写它，那里面是**上一个不相关系统调用**的残留值。

正确写法三个细节缺一不可：

```cpp
const int mask_error = ::pthread_sigmask(SIG_BLOCK, &stop_mask, nullptr);
if (mask_error != 0) {
    throw std::system_error(mask_error, std::generic_category(),
                            "阻塞停止信号失败");
}
```

判断用 `!= 0`（不是 `< 0`）；错误码用**返回值本身**（不是 errno）；完全不碰 errno。

**更大的教训**：Linux 里"怎么算失败"没有统一规则，**按函数族分派**。反例：`sem_post` / `sem_wait` / `sem_init` 站在 syscall 那一边（失败 -1 且设 errno），所以"`pthread_` 开头"也不能当判据，只有查文档靠得住。

## Q4　集中理解检查第 2 题：eventfd 与 signalfd 各通知什么？

### 4.1 eventfd 通知"工作线程往完成队列里放了一条结果"

生产者是 2 条 worker 线程，消费者只有事件循环那 1 条。它是 8 字节的无符号 64 位**计数器**，worker 每次只写常量 `1`。

真正的业务数据在**另一个地方**：`completed_` 这个 deque，里面有 `connection_token`、`worker_index`、`output`、`error`，由 `completed_mutex_` 保护。

**eventfd 是门铃，不是快递。** 最直接的证据是 `drain_notifications()` 里那句注释：

```cpp
if (received == static_cast<ssize_t>(sizeof(count))) {
    continue; // 数值不用于决定取多少条结果。
}
```

读出来的数值被直接扔掉，读它只为把计数器清零（让 LT epoll 别再反复报可读）。取多少条看 deque 的实际长度。

**设计意图**：deque 才是唯一权威，eventfd 只是"去看看"的提示。哪怕某次写通知失败，也不会让你取错条数。

### 4.2 signalfd 通知"有被屏蔽的信号变成 pending 了"

读出来的是 `signalfd_siginfo` 结构体（**不是** 8 字节计数器），`ssi_signo` 告诉你是 SIGINT 还是 SIGTERM。

**读走 = 消费掉这个 pending 信号。** 不读，LT epoll 会一直报可读。

### 4.3 对比

| | eventfd | signalfd |
| --- | --- | --- |
| 通知什么 | 线程池有结果交回 | 有指定的停止信号 pending |
| 触发源 | **你自己的 worker 线程** | **内核** |
| 读出来是什么 | 8 字节 uint64 计数 | `signalfd_siginfo` 结构体 |
| 有业务数据吗 | 没有，数据在 `completed_` 里 | 没有，信号本身就是全部信息 |
| 读它的意义 | 清计数、按停门铃 | 消费 pending 信号 |
| epoll token | 1（completion_token） | 2（stop_token） |

**共同的本质**：两者都是把一种**异步事件**翻译成 epoll 能等的**可读 fd**。有了这两个翻译器，事件循环就成了整个程序**唯一的决策点**。

### 4.4 close_connection 和打印日志是在异步信号回调里吗？—— 不是

本课**根本没有安装任何信号处理函数**（没有 `signal()`，没有 `sigaction()`）。

```text
Ctrl+C  →  内核置 pending（因为没有线程解除屏蔽）
        →  signalfd 变可读
        →  epoll_wait 返回              ← 以上全是内核在干活
        ──────────────────────────────  ← 以下全是普通用户代码
        →  take_stop_signal()  普通函数调用
        →  begin_stop()        普通函数调用
        →  close_connection() / std::cout   ← 想怎么用就怎么用
```

**措辞上值得较真**：`take_stop_signal` 和 `begin_stop` 是**普通函数**，不是 callback。callback 是"你注册、别人在不确定的时刻调用你"；这里是"你在固定位置调用、在你自己确定的时刻执行"。**这个区别就是安全与不安全的分界线。**

因为全线程屏蔽 + 无 handler，信号在这个进程里**只有 signalfd 这一个出口**——"信号路径唯一"意味着你永远不会面对"我到底是在正常上下文还是在信号上下文"这种问题。

### 4.5 附带澄清：三个数各管各的

| | 含义 | 谁维护 |
| --- | --- | --- |
| eventfd 计数 | 还没被事件循环读走的通知条数 | 内核计数器 |
| `completed_` 长度 | 真有几条结果待取 | `completed_mutex_` 保护的 deque |
| `outstanding_` | 已接受但还没交回的任务数，也用来卡 4 个上限 | 只由事件循环读写 |

`take_completed` 里有一句防御：`if (ready.size() > outstanding_) throw std::logic_error(...)`——查的就是"账面跟实物对不上"。

## Q5　集中理解检查第 3 题：四种资源为什么区别处理？

分野只有一条标准：**这笔工作有没有产生"必须被交付的成果"**。

| 资源 | 处理 | 理由 |
| --- | --- | --- |
| listener | epoll DEL + `reset()` 真关掉 | 关掉它，"不再有新工作进来"才是事实。只 DEL 不 close 还占着 fd |
| 半截请求（header/body） | 立刻关闭 | 还没提交成业务任务，没有成果可交付，留着又让 `connections.empty()` 永远不满足。不把它伪装成成功响应 |
| waiting_result | 保留 | 任务已交出去，一份真实结果正在路上。删了连接，结果回来无处可送，账也对不上 |
| sending | 保留 | 响应已准备好、可能已发一半，删掉就是丢弃已完成的劳动 |

### 为什么关了队列不能立即 join

`close` 只表示"拒绝新任务、允许取完已有任务"。而 worker 算完后要把结果推进 `completed_` 并写 eventfd——**这些结果只有事件循环能取、只有事件循环能发**。

一旦先 join，事件循环线程就停摆了：结果没人取、EPOLLOUT 没人处理，已经准备好的响应全丢。所以顺序只能是：先排空 → 循环条件满足 → 最后析构 pool 时才 join。

## Q6　集中理解检查第 4 题：退出条件为什么必须三项？

```cpp
while (!stopping || pool.outstanding() != 0 || !connections.empty())
```

| 项 | 堵的洞 |
| --- | --- |
| `!stopping` | 没收到停止请求时，空闲也该继续监听。缺了它，服务端在没有连接的一瞬间就自己退出了 |
| `outstanding() != 0` | 结果可能还没产生，worker 还在算 |
| `!connections.empty()` | 结果已取回、outstanding 归 0，但 `Connection::output` 还有字节没发完 |

只看后两项之一会提前退出：

- **只看 `outstanding`**：结果取回后计数归 0，但连接正处于 sending、output 里还有半截 → 提前退出，客户端拿到截断响应。这正是 10-1 记录里 204、205 那两条 10 秒 ok 会消失的场景。
- **只看 `connections`**：连接可能已超时被 `expire_connections` 删掉，而 worker 仍在算 → 提前退出，那条"过期结果"永远不被取回、额度不释放。

## Q7　集中理解检查第 5 题：30 秒到期与"永不返回"

**请求等待超过 30 秒、连接已关闭 → 不保证 worker 已停止。**

那个 30 秒期限作用在**连接**上，只是网络层的收尾规则，它不碰 worker、也不取消任何任务——C++ 标准线程本来就没有安全的强制取消机制。worker 会把当前任务算完、发布结果，事件循环再把它当"过期结果"取回并丢弃。

（顺带：还有一条 10 秒"无收发进展"规则作用在发送阶段，同样不涉及 worker。）

**计算永不返回 → 不能保证有限时间退出。**

退出条件要求 `outstanding == 0`，而它只在任务真正交回时才减。任务卡死 → outstanding 永不为 0 → 永远停在 stopping。再按 Ctrl+C 只打印"已经在停止"，join 也永远等下去。

这是 10-1 明确划下的边界：本课实现的是**合作式**停止——它需要被停止者的配合。要**保证**有限时间退出，只能靠进程外的监管者上 SIGKILL，因为 SIGKILL 不需要谁的同意。

# 第二部分　10-2 父子进程、程序启动与退出回收

## Q8　为什么新模块要设父子进程？相比线程池有什么好处？

### 8.1 先纠正前提：不是替代，是叠加

```text
process_launcher（父，单线程，只管生死）
  └─ vision_pool_server（子，事件循环 + 2 条 worker 线程）
        └─ ImageWorkerPool ← 线程池原封不动在里面
```

线程池管的是"**在一个进程内部让多核并行干活**"（吞吐）；父子进程管的是"**谁来照看这个进程的生死**"（可用性与可控性）。服务端源码一个字都不用改。

### 8.2 根本区别只有一句话

**线程共享同一个地址空间，进程不共享。** 这一条推演出后面所有的好处。

| | 线程 | 父子进程 |
| --- | --- | --- |
| 地址空间 | 共享 | 独立（页表隔离） |
| 一个 worker 段错误 | **整个进程一起死**，日志都写不出去 | 只有子进程死，父进程活着，能记录、能决策 |
| 崩溃归因 | 没有内核级接口 | `waitpid` 的 status：退出码多少，或被**哪个信号**杀死 |
| 强制终止 | 没有安全的手段 | `SIGKILL`，内核直接拆掉地址空间，不需要对方配合 |
| 资源回收 | 靠 RAII 写全，漏了就漏了 | 内核回收该进程所有 fd／内存／线程 |
| 通信 | 直接读写内存，一把 mutex 就够 | 要 pipe／socket，得自己定协议 |
| 启动成本 | 低 | fork + exec + 动态链接，明显更贵 |

### 8.3 具体到本项目的好处

1. **这是 10-1 那堵墙的唯一出口。** 10-1 的结论是"不承诺强制停止期限"，因为任务卡住 `outstanding` 永远不为 0。线程无解：C++ 标准没有安全的线程取消，`pthread_cancel` 能在任意点撕开一条线程，留下半锁的 mutex、半改的容器。**"保证有限时间退出"只有进程边界能提供。**
2. **监管者必须站在被监管者倒下的范围之外。** 线程做不到——进程一崩，那条负责强杀的线程也一起没了。**先有进程边界，监管才有立足点。**
3. **失败可以归因，且不可伪造。** `WIFEXITED` / `WIFSIGNALED` + `WTERMSIG` 是内核发的死亡证明。10-2 的 14.4 就是例子：被信号终止时启动器报告"信号编号 15"、返回 143，而**目标程序根本没执行过 `return 143`**。
4. **有重启和升级的位置。** 进程死了可以再 fork 一个；`exec` 的语义是"同一个 PID 换一个程序映像"——线程无法"换掉自己"。
5. **内核级的边界。** 独立 PID 意味着可以被 systemd／cgroup 管、可以有独立资源限额、可以被单独 strace、可以降权运行。

### 8.4 代价

- **通信变贵**：进程之间要管道，还得自己定协议——`LaunchError{stage, code}` 就是这笔税。
- **fork 与多线程天生冲突**：多线程进程 fork 出的子进程只保留调用 fork 的那一条线程，却可能复制了别的线程持有的锁状态（锁处于"锁着但没有持有者"的死状态）。所以启动器必须**自己保持单线程**，先 fork 再 exec：**让父进程保持简单，让子进程 exec 出一个复杂的世界**。
- **多出僵尸进程这个新问题**：需要 `waitpid` 回收。
- **父子不共享变量**：所有信息必须显式过管道传。

### 8.5 一句话总结

线程池回答"**怎么把活干完**"，父子进程回答"**活干不完、或者干崩了的时候怎么办**"。

顺带一提：shell 执行 `./a.out` 就是 fork + exec + wait；nginx、systemd、docker 全是这一套。

## Q9　10-2 集中理解检查五题（简要）

### 9.1 fork 的返回值与 execv

- 父分支：正数 = **子进程的 PID**；子分支：**0**；失败：**-1** + errno。
- **0 不是 PID**，它只是 fork 的返回值，一个"你是孩子"的哨兵。子进程真实的 PID 只有父分支知道；子进程想知道自己的号，得自己 `getpid()`。
- execv 成功：**既不创建第三个进程，也不返回**。PID 不变，还是同一个进程，只是程序映像被换掉了——下一句永远执行不到。

### 9.2 argv+1 与为什么必须 `_exit`

`execv(path, argv + 1)` 把 `argv[1]` 变成新程序的 `argv[0]`，后面的顺次前移。启动器的 `argv[0]`（自己的路径）不会传给孩子。

为什么不能 `return`：子进程是父进程的副本，`return` 会让它**回到 main 的后半段继续跑**——那时 `child_pid` 是 0，它会去构造 `ChildProcess child(0)`、打印"父进程"的日志、去读错误报告……子进程会冒充父进程把整套流程走一遍。

也不能用 `exit()`：它会刷 stdio 缓冲、跑 atexit，把 fork 前缓冲里的内容**重复输出**一遍。所以只能用 `_exit(127)`——不清理、不刷缓冲，就地结束这条分支。

### 9.3 FD_CLOEXEC 与父进程的写端

- 关闭时机是**exec 成功那一刻**，由内核自动完成。它不阻止 fork 继承，也不是调用 fcntl 时立刻关。
- 父进程也持有一份写端副本。管道 EOF 的条件是"**所有**写端都关闭、已写数据也读尽"。父进程不 `reset()` 自己的写端，即使子进程那份已随 exec 关掉，管道里仍有一个活着的写端 → 父进程**永远读不到 EOF，卡死在 `read_launch_error`**。
- **无报告的 EOF 不足以证明服务端已监听。** 它也可能来自：子进程在提交报告前被信号打死；动态加载器失败（exec 已完成但程序没起来）。所以日志措辞是"未收到失败报告"，不是"启动成功"。要确认就绪，只能看服务端自己的监听提示或实际连上去。

### 9.4 三种 127 与 status

| | `return 127` | execv 失败 |
| --- | --- | --- |
| 子进程退出码 | 127 | 127（`_exit(127)`） |
| 错误管道 | 无报告 | 有 `LaunchError`（阶段 + errno） |
| **启动器返回** | **127** | **125** |

只看子进程退出码无法区分，这正是那条专用管道的全部意义。

三个数字别混：

- `waitpid` 的**返回值**是 `pid_t`——被回收子进程的 PID（或 -1 失败），不是状态。
- `status` 是输出参数，**内核编码的复合值，不是裸退出码**。必须先分类再取字段。
- `WEXITSTATUS` **只在 `WIFEXITED` 为真时有效**。

信号终止：`WIFSIGNALED` 为真 → `WTERMSIG` 取信号编号（SIGTERM = 15）。此时**绝不能调 `WEXITSTATUS`**——那几个 bit 含义完全不同。启动器按自己的约定返回 `128 + 15 = 143`，**这不是目标程序 return 了 143**，它根本没走到正常 return。

### 9.5 信号的两侧设置

- 前台运行时父子同在终端的前台进程组，Ctrl+C 由终端**同时**通知两者。父若也被打死，就没人回收孩子、没人报告退出状态——所以它忽略 SIGINT，专心做 waitpid。
- 子进程必须恢复 `SIG_DFL` 并解除屏蔽：忽略动作和屏蔽集合都会从父进程继承，而 `SIG_IGN` 这类动作**跨 exec 保留**。不恢复的话，目标程序会对 Ctrl+C 莫名其妙地免疫。
- **当前代码没有父进程主动转发信号。** 孩子收到的那份 SIGINT 是终端直接发给进程组的。
- **`waitpid` 不能强制孩子结束。** 它只负责"等"和"回收"，不控制对方。孩子卡住，父进程就永远阻塞在 `waitpid`（本课用的是不带 `WNOHANG` 的阻塞等待）。宽限期和强制终止属于 10-3。
